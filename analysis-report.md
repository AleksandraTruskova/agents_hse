# Отчёт по анализу работ: direct и with-spec

Дата анализа: 2026-11-23. Анализировались обе папки без внесения изменений.
Брифы в обеих папках идентичны (побайтово совпадают).

## 1. direct — качество реализации

Структура соответствует варианту B брифа: `index.html`, `styles.css`, `app.mjs`, `domain.mjs`, `tests/acceptance.test.mjs`, плюс `report.md`.

Архитектура чистая: доменная логика без DOM вынесена в `domain.mjs` (валидация, статистика, add/remove/toggle, фильтр), `app.mjs` — только связка с DOM. Операции возвращают новые коллекции (без мутаций), id — числовые инкрементальные.

Соответствие brief.md — полное:
- добавление/удаление/переключение done реально меняют данные — да;
- валидация: trim названия, часы 0,5–24 с шагом 0,5, пустое значение ≠ 0, ошибка рядом с полем, значения формы сохраняются — да (`validateTaskInput`, ранний return в app.mjs без сброса полей);
- прогресс = round(100 × done/total), при пустом списке 0% без NaN — да;
- фильтр влияет только на список, итоги по всем задачам — да;
- стартовые 8 ч / 2 ч / 25%, «Практика» → 6/8 / 75% — да;
- 390 px без горизонтального скролла, подписанные поля — да (box-sizing, max-width 480, flex-wrap);
- необязательное улучшение (localStorage + сообщение при недоступности) — реализовано.

Сверх брифа: третий фильтр «Готовые», прогресс-бар с ARIA, сообщение пустого списка, `aria-pressed`/`role=progressbar`.

## 2. with-spec — качество реализации

Та же модульная структура. Архитектура тоже двухслойная, но оформлена формальнее: репозиторий хранилища с пробой localStorage и in-memory fallback, id через `crypto.randomUUID()` с fallback, различение «пустое хранилище» и «сохранённый пустой список» (последнее — плюс к direct, где отдельного теста на это нет).

Соответствие brief.md — полное по всем шести требованиям и WHEN/THEN-приёмке (логика идентична по смыслу). Необязательное улучшение localStorage реализовано.

Соответствие спецификации (`openspec/changes/build-tracker/`):
- Все требования spec.md покрыты кодом и тестами: управление задачами, валидация названия/часов, стартовые данные, прогресс по часам, пустое состояние, фильтр, localStorage с деградацией, автономность — да.
- design.md соблюдён: два слоя, репозиторий с fallback, защита от деления на ноль конструкцией, числовая валидация, randomUUID.

Процессные расхождения со spec-driven workflow:
- В `tasks.md` не отмечены выполненными задачи 3.1–3.6 (интерфейс) и 4.1 (прогон T1–T5 в браузере), хотя код интерфейса существует, а скриншоты доказывают браузерный прогон. Трекинг задач не актуализирован.
- Изменение не заархивировано: `openspec/changes/archive/` пуст, несмотря на пункт «Workflow follow-up».
- Задача 4.2 отмечена выполненной («список фактических проверок записан»), но такого файла в папке нет — у direct есть `report.md`, у with-spec отчёта нет.
- В корне with-spec лежат два скриншота-дубликата (есть в `screenshots/`).

## 3. Тесты (фактически запущены при анализе, Node v26.13.1)

- direct: `node --test tests/` — 10/10 зелёные (T1–T5, включая границы/шаг часов, нечисловой ввод, trim).
- with-spec: `node --test tests/` — 8/8 зелёные (T1–T5 + персистентность, сохранение пустого списка, недоступное хранилище).
- Покрытие у обоих адекватное; у direct тесты детальнее по валидации (9 подслучаев T4), у with-spec — по хранилищу.

## 4. Оформление (визуал)

- direct: аккуратная карточная вёрстка, единая сине-серая палитра, стилизованные кнопки фильтров с активным состоянием, прогресс-бар, зачёркнутые выполненные задачи, сообщение пустого списка. Выглядит как готовый продукт.
- with-spec: минимальная вёрстка на «дефолтных» контролах браузера, без прогресс-бара и цветовых акцентов; часы вписаны в текст задачи, итоги — простая строка текста. Функционально, но заметно проще и «сырее» визуально.

## 5. Почему в direct есть фильтр «Готовые», а в with-spec — нет

Это следствие разницы процессов, а не баг:

- Бриф явно не требует фильтра «готовые» — только «фильтр влияет на список» и приёмку для фильтра «активные».
- В direct агент по своему усмотрению добавил третий фильтр «Готовые» (all/active/done в `domain.mjs`).
- В with-spec состав фильтра был зафиксирован на этапе спецификации: `proposal.md` — «фильтр "активные/все"», `spec.md` содержит сценарий только для «активных». Реализация строго следует спецификации (`FILTERS = { ALL, ACTIVE }`, в `<select>` два пункта) — ровно столько, сколько задано, без самодеятельности. Поэтому посмотреть только выполненные задачи в with-spec нельзя — что и зафиксировано на скриншоте «Видно что не хватает выполненных задач в фильтре.png». Формально это соответствие спецификации, а не дефект; по сути — сужение брифа при написании спеки.

## Вывод

Обе реализации корректны, тесты зелёные, брифу соответствуют обе. direct — богаче по UI и UX-деталям и имеет честный `report.md`. with-spec — строже по архитектуре хранилища и процессу (proposal/design/spec), но: спека сузила фильтр до двух значений, чекбоксы задач интерфейса не отмечены, изменение не заархивировано, итоговый отчёт о проверках отсутствует.
