# Spec Delta

## Purpose

Возможность вести список учебных задач на неделю: добавлять, удалять и отмечать задачи, видеть итоговые часы и прогресс по часам, фильтровать список и сохранять данные между запусками — полностью локально в браузере.

## ADDED Requirements

### Requirement: Управление задачами
Система SHALL позволять добавлять задачу с названием и часами, удалять задачу и переключать её готовность (`done`). Каждая операция MUST реально изменять данные, после чего интерфейс MUST отражать новое состояние списка и итогов.

#### Scenario: Добавление задачи
- **WHEN** пользователь вводит корректное название и часы и отправляет форму
- **THEN** задача появляется в списке, итоговые часы и прогресс пересчитаны

#### Scenario: Удаление задачи
- **WHEN** пользователь удаляет существующую задачу
- **THEN** задача исчезает из списка, итоговые часы и прогресс пересчитаны по оставшимся задачам

#### Scenario: Переключение готовности
- **WHEN** пользователь отмечает «Практику» (4 ч) готовой при исходных данных
- **THEN** выполнено 6 из 8 часов, прогресс 75%, и данные, и интерфейс изменились

### Requirement: Валидация названия задачи
Система SHALL принимать название только если после `trim` оно непустое. Иначе задача MUST NOT добавляться, рядом с полем названия MUST отображаться ошибка, а введённые значения формы MUST сохраняться для исправления.

#### Scenario: Пустое название или пробелы
- **WHEN** пользователь отправляет форму с пустым названием или только из пробелов
- **THEN** задача не добавляется, видна ошибка рядом с полем названия, введённые значения остались в форме

### Requirement: Валидация часов задачи
Система SHALL принимать часы только как число от 0,5 до 24 с шагом 0,5. Пустое значение MUST NOT трактоваться как ноль: оно MUST считаться ошибкой. Иначе задача MUST NOT добавляться, рядом с полем часов MUST отображаться ошибка, а введённые значения формы MUST сохраняться для исправления.

#### Scenario: Пустые часы
- **WHEN** пользователь отправляет форму с пустым полем часов
- **THEN** задача не добавляется, видна ошибка рядом с полем часов, введённые значения сохранены

#### Scenario: Отрицательные часы
- **WHEN** пользователь отправляет форму с отрицательными часами
- **THEN** задача не добавляется, видна ошибка рядом с полем часов

#### Scenario: Нарушение границ 0,5–24
- **WHEN** пользователь отправляет часы меньше 0,5 (например, 0,3) или больше 24
- **THEN** задача не добавляется, видна ошибка рядом с полем часов

#### Scenario: Нарушение шага 0,5
- **WHEN** пользователь отправляет часы, не кратные 0,5 (например, 1,3)
- **THEN** задача не добавляется, видна ошибка рядом с полем часов

### Requirement: Стартовые данные
При первом запуске, когда хранилище пусто, система SHALL показывать три стартовые задачи: «Чтение» — 2 ч, готово; «Практика» — 4 ч, активно; «Повторение» — 2 ч, активно.

#### Scenario: Первый запуск
- **WHEN** пользователь открывает приложение при пустом хранилище
- **THEN** в списке три задачи: «Чтение» (2 ч, готово), «Практика» (4 ч, активно), «Повторение» (2 ч, активно); всего 8 часов, выполнено 2 часа

### Requirement: Прогресс по часам
Система SHALL вычислять прогресс как округление(100 × сумма часов готовых задач / сумма часов всех задач) — по часам, а не по числу задач. Итоговые выполненные часы MUST показываться вместе с прогрессом.

#### Scenario: Исходный пример
- **WHEN** открыты три стартовые задачи
- **THEN** прогресс 25% (2 из 8 часов), а не 1/3 по числу задач

#### Scenario: Отметка «Практики» готовой
- **WHEN** «Практика» отмечена готовой
- **THEN** прогресс 75% (6 из 8 часов)

### Requirement: Пустое состояние
Когда задач нет, система SHALL показывать 0 часов и 0% прогресс. Расчёт MUST NOT производить NaN или Infinity, интерфейс MUST продолжать работать, включая добавление новой задачи.

#### Scenario: Все задачи удалены
- **WHEN** пользователь удалил все задачи
- **THEN** итог 0 ч, прогресс 0%, значений NaN/Infinity нет, интерфейс работает

### Requirement: Фильтр списка
Система SHALL предоставлять фильтр, влияющий только на видимый список. Итоговые часы и прогресс MUST считаться по всем задачам независимо от фильтра.

#### Scenario: Фильтр «активные»
- **WHEN** включён фильтр «активные» при исходных данных
- **THEN** в списке только «Практика» и «Повторение», а общий прогресс остаётся 25%

### Requirement: Сохранение в localStorage
Система SHALL сохранять задачи в localStorage при каждом изменении и загружать их при старте. Если localStorage недоступен (запрещён, переполнен или бросает исключение), система MUST показать понятное сообщение и продолжить работу в памяти.

#### Scenario: Данные сохраняются между запусками
- **WHEN** пользователь добавил или изменил задачи и перезапустил приложение
- **THEN** список восстановлен из localStorage

#### Scenario: Недоступное хранилище
- **WHEN** localStorage недоступен при любом действии с данными
- **THEN** показано понятное сообщение о недоступности сохранения, приложение продолжает работать в памяти

### Requirement: Читаемость на узком экране
Интерфейс MUST быть читаемым при ширине 390 px без горизонтального скролла. Поля ввода и кнопки MUST иметь видимые подписи (label).

#### Scenario: Ширина 390 px
- **WHEN** приложение открыто при ширине viewport 390 px
- **THEN** контент читаем, горизонтального скролла нет, поля и кнопки подписаны

### Requirement: Автономность приложения
Приложение SHALL работать полностью локально: без CDN, внешних библиотек, сетевых запросов и API-ключей.

#### Scenario: Работа без сети
- **WHEN** пользователь открывает приложение без доступа к сети
- **THEN** трекер загружается и полностью работает
